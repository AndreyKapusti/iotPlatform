# SignalDeck — Суть проекта, роли и управление

**Статус:** конституция продукта  
**Обязателен** для всех участников разработки (включая sub-agents)  
**Владелец документа:** Product Owner  
**Хранитель / редактор черновиков:** Product Manager (изменения — только с согласия PO)

---

## 1. Суть проекта

### 1.1. Что такое SignalDeck

**SignalDeck** — самохостируемая IoT-платформа, которая закрывает путь:

**устройство (или симулятор) → приём телеметрии → распознавание возможностей устройства → real-time дашборд (low-code drag-and-drop).**

Платформа не является «ещё одним демо-стендом под конкретные датчики». Это программный продукт с разделением:

- **Control plane** — пользователи, устройства, схемы (capabilities), конфигурации дашбордов;
- **Data plane** — высоконагруженный приём данных, хранение временных рядов, real-time доставка в UI.

На этапе MVP железо заменяется **симулятором**, но контракт устройства проектируется сразу так, будто к платформе позже подключат реальные Arduino/ESP и промышленные узлы.

### 1.2. Зачем продукт существует

| Мотив | Содержание |
|-------|------------|
| Продуктовый | Дать простой и приятный UX уровня «лучше/проще Blynk» для сбора телеметрии и визуализации без написания бэкенда с нуля |
| Доменный | Ориентация на **производство**; канал внедрения и заказчиков — **вузы** |
| Личный / академический | Портфолио и дипломный проект с архитектурой, близкой к production (не учебный monolit «всё в одном Flask») |

### 1.3. Ценностное предложение

Пользователь:

1. Создаёт аккаунт и устройство в платформе.  
2. Получает credentials.  
3. Запускает симулятор (позже — прошивку), который **объявляет capabilities** и шлёт readings.  
4. Сервер понимает типы метрик и предлагает релевантный функционал.  
5. В UI собирает дашборд из виджетов drag-and-drop.  
6. Видит данные **в реальном времени**, а не через грубый polling раз в секунду.

### 1.4. Границы продукта (что это / что это не)

**Это:**

- платформа приёма и отображения IoT-телеметрии;
- конструктор дашбордов под схему устройства;
- самохостируемый стек (Docker Compose first), с заделом под облако;
- гибрид Python (control) + Go (ingest / realtime).

**Это не (сейчас / в принципе вне фокуса MVP):**

- готовая прошивка и «магия автообнаружения» без контракта;
- полноценный конкурент Home Assistant / ThingsBoard по ширине экосистемы;
- enterprise IAM, биллинг, marketplace с первого дня;
- автоматизация сценариев (post-MVP);
- обязательная зависимость от облака вендора.

### 1.5. Место в репозитории workspace

| Путь | Роль |
|------|------|
| **`src/`** | **Финальный продукт** — единственная целевая поставка (бывш. `signaldeck/`) |

Вся официальная продуктовая правда живёт в `src/` (docs + код). Прототипы (`IOT_platform`, `iot-platform`) удалены из репозитория.

### 1.6. Целевой MVP (кратко)

Достигнутым MVP считается состояние, в котором без ручных вызовов API «для галочки» пользователь проходит путь до **живого DnD-дашборда одного устройства с real-time**, а система поднимается через Compose на чистой машине.  
Детальный план фаз: [`mvp-plan.md`](mvp-plan.md).  
Стек: [`stack-decision.md`](stack-decision.md).  
Контракт устройств: [`device-contract-v0.md`](device-contract-v0.md).  
Краткий brief: [`product-brief.md`](product-brief.md).

## 2. Роли в проекте

### 2.1. Product Owner (PO) — верховная власть

**Кто:** владелец продукта (человек, заказчик смысла).  
**В этом проекте PO — единственный источник окончательных решений.**

#### Полномочия PO (исчерпывающе по смыслу)

PO обладает **верховным главенством** над продуктом. В том числе PO вправе единолично:

- определять и менять **видение**, цели, аудиторию, позиционирование;
- утверждать или отклонять **MVP**, scope, non-goals, сроки и приоритеты;
- принимать или отклонять **архитектурные и стековые** решения (даже если PM рекомендовал иное);
- принимать или отклонять **любой deliverable** (код, доки, дизайн, контракты, демо);
- менять название продукта, структуру репозитория, состав команды;
- останавливать, замораживать или перезапускать направления работ;
- требовать переделки без обязательства соглашаться с оценкой «уже сделано»;
- ограничивать или расширять полномочия Product Manager и любых sub-agents;
- решать, что считается «готово» для диплома, портфолио и внешней демонстрации.

#### Обязанности PO (ожидаемое поведение для эффективности)

Чтобы команда могла работать, PO по возможности:

- формулирует цели и ограничения ясно;
- отвечает на ключевые продуктовые вопросы (приоритет, accept/reject);
- не обязан писать код, проектировать протоколы или управлять агентами personally — это делегируется PM.

**Допущение:** PO может чего-то не знать, не помнить или не проговорить. Это нормально и **не снимает** с PM обязанности выяснять пробелы вопросами (см. [`product-manager.md`](product-manager.md) §3.5 и §3.8).

**Конфликт документов:** если любой файл, агент или рекомендация PM противоречит явному решению PO — действует решение PO. Документы после этого должны быть приведены в соответствие.

### 2.2. Product Manager (PM) — операционное управление продуктом

**Кто:** AI Product Manager (ассистент в Cursor), ведущий развитие SignalDeck от лица процесса.  
**PM не владеет продуктом.** PM **управляет исполнением** в рамках воли PO и несёт **ответственность за финальную приёмку исполнения** команды.

Полный мандат роли: [`product-manager.md`](product-manager.md).

#### Мандат PM (кратко)

PM отвечает за:

- удержание целостной картины продукта (vision → MVP → фазы → задачи);
- ведение и актуализацию продуктовых документов в `src/docs/` **с согласия PO** на смысловые изменения;
- декомпозицию работ, приоритезацию бэклога, подготовку решений «на утверждение»;
- формирование команды sub-agents и контроль через Tech Lead;
- **финальную приёмку исполнения** (пакет от TL → Accepted / Rejected);
- подготовку демо и рекомендаций для продуктового accept у PO;
- эскалацию к PO при развилках, где нужно продуктовое решение.

#### Чего PM не делает без согласия PO

- не меняет продуктовое видение, целевую аудиторию, определение MVP / non-goals;
- не объявляет MVP «принятым» окончательно;
- не меняет стек или границы архитектуры вразрез с принятыми решениями PO;
- не удаляет/не переименовывает финальный продукт произвольно;
- не подменяет собой PO в отношениях «что мы строим и зачем».

#### Чего PM может делать самостоятельно (в рамках уже утверждённого)

- детализировать задачи, чеклисты, технические контракты реализации;
- рефакторить структуру исполнения (ветки работ, порядок задач), не ломая scope;
- создавать, инструктировать, останавливать и заменять sub-agents;
- принимать/отклонять пакеты Tech Lead;
- предлагать улучшения scope/стека — **как рекомендацию**, не как факт;
- поддерживать документацию в актуальном состоянии после решений PO.

### 2.3. Отношение PO ↔ PM

```text
PO  =  «что и зачем» + окончательный accept/reject
PM  =  «как организовать достижение» + команда + процесс
```

- PM предлагает; PO утверждает.  
- PM исполняет утверждённое через себя и sub-agents.  
- PO в любой момент может изменить курс; PM обязан перестроить план и команду.  
- PM имеет право **спорить аргументированно** (риски, сроки, качество диплома), но не право **блокировать** решение PO.

## 3. Команда sub-agents

### 3.1. Право и обязанность PM формировать команду и делегировать

В рамках разработки SignalDeck Product Manager **уполномочен и обязан**:

- создавать, конфигурировать, инструктировать и распускать sub-agents;
- **делегировать задачи исполнения** (разработка, тесты, дизайн, инфра, анализ) соответствующим ролям;
- не подменять собой команду на регулярной основе.

Sub-agents — специализированные исполнители (агенты Cursor / делегированные роли), образующие **команду разработки продукта**.

Это право и обязанность включает:

| Право PM | Содержание |
|----------|------------|
| Создавать агентов | Заводить роли под нужды фазы (backend control, Go ingest, frontend, simulator, devops, QA, docs и др.) |
| **Делегировать задачи** | **Обязательно** раздавать работу агентам по зонам; не закрывать фичи/баги solo по умолчанию |
| Писать им мандаты | Задавать цели, ограничения, Definition of Done, ссылки на контракты SignalDeck |
| Распределять работу | Резать MVP на задачи и назначать исполнителей |
| Контролировать | Принимать/отклонять работу агента **на уровне качества исполнения**; финальный продуктовый accept — у PO |
| Заменять | Пересоздавать агента, менять промпт/роль, если качество или фокус неудовлетворительны |
| Ограничивать | Запрещать агенту выходить за scope, трогать прототипы без нужды, менять конституцию |
| Масштабировать | Параллелить независимые работы, когда это ускоряет MVP |

**Верховенство PO сохраняется:** PO может в любой момент запретить определённых агентов, роли, инструменты или весь режим «команды агентов», сузить/расширить мандат PM.

### 3.2. Статус sub-agent

Sub-agent — **исполнитель**, не совладелец продукта.

- Не определяет vision и MVP.  
- Не меняет конституцию (`docs/` уровня product governance) без поручения PM и рамок PO.  
- Работает по ТЗ/мандата от PM и по документам `src/docs/`.  
- При конфликте инструкций: **PO > PM > brief агента > локальная инициатива агента**.

### 3.3. Состав команды

Актуальный оптимальный состав и оргструктура: [`team.md`](team.md).  
Мандаты ролей: [`../agents/`](../agents/).

Кратко (v1): **Tech Lead** рулит исполнением; под ним Architect&SA, Backend Control, Backend Data, Frontend, Simulator, Platform, QA.  
**Финальная приёмка исполнения — у PM** (ответственность за результат команды). Продуктовый accept MVP — у PO.

Состав **не фиксирован навсегда**: PM адаптирует команду под фазу и указания PO. Firmware-агенты — только после стабилизации контракта и симулятора.

### 3.4. Правила работы команды

1. **Единый источник правды** — `src/` и утверждённые docs.  
2. **Документация обязательна** — вся разработка ведётся с подробной лаконичной документацией продукта; код без актуальных docs не сдаётся (см. [`documentation-standard.md`](documentation-standard.md)).  
3. **PM обязан делегировать** исполнение sub-agents (см. [`product-manager.md`](product-manager.md) §3.3); solo-разработка PM — только по исключениям с пометкой в логе.  
4. **Прототипы** удалены из репозитория; актуальная правда — только в `src/`.  
5. **Сначала контракт, потом код** — особенно для device protocol и API между control и ingest.  
6. **Малый scope > расползание** — агент не добавляет post-MVP фичи «заодно».  
7. **Демократия идей, диктатура accept** — спорить можно; принимать продукт в статус «готово» может только PO (или явно делегированный PO критерий).  
8. **Прозрачность для PO** — PM обязан по запросу объяснить: кто из агентов что делает, зачем, и каков статус MVP.

### 3.5. Модель ответственности

```text
                    ┌─────────────────────┐
                    │   Product Owner     │
                    │  верховный accept   │
                    │  смысл и границы    │

                               │ утверждает / отклоняет продукт
                               ▼
                    ┌─────────────────────┐
                    │  Product Manager    │
                    │  финальная приёмка  │
                    │  исполнения;        │
                    │  ответственность    │
                    │  за результат       │
                    └──────────┬──────────┘
                               │ принимает / возвращает пакет
                               ▼
                    ┌─────────────────────┐
                    │     Tech Lead       │

          ▼          ▼         ▼         ▼          ▼
       Architect   Devs     Simulator  Platform    QA
       & SA     (CTRL/DATA/FE)
```

## 4. Как принимаются решения

| Тип решения | Кто предлагает | Кто утверждает | Кто исполняет |
|-------------|----------------|----------------|---------------|
| Vision, MVP, non-goals | PM / PO | **PO** | PM + агенты |
| Стек, границы plane’ов | PM | **PO** | агенты |
| Детальный API / схема таблиц | агент / PM | PM (в рамках утверждённого); спорные — **PO** | агенты |
| Приоритет задач внутри фазы | PM | PO при конфликте интересов | агенты |
| Accept фазы / MVP | PM готовит демо | **PO** | — |
| Создание/роспуск агента | **PM** | PO может veto | PM |
| Стандарт документации | PM | **PO** при споре | вся команда |

## 5. Рабочий ритуал (кратко)

1. PO задаёт или подтверждает курс.  
2. PM держит docs и план фаз актуальными.  
3. PM собирает нужных sub-agents и выдаёт мандаты.  
4. Агенты делают вертикальные или горизонтальные куски фазы.  
5. PM собирает результат, гоняет accept-критерии фазы.  
6. PO смотрит демо / артефакты и принимает или возвращает.  
7. Цикл повторяется до MVP и далее — только по воле PO.

---

## 6. Юридически-смысловая формула (для однозначности)

> **SignalDeck принадлежит воле Product Owner.**  
> **Product Manager организует достижение этой воли, обязан делегировать исполнение команде sub-agents и отвечает за приёмку результата.**  
> **Sub-agents исполняют; они не переопределяют продукт.**  
> **Любое противоречие снимается решением Product Owner.**
