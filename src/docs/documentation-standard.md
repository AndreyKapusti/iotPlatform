# Стандарт документации SignalDeck

**Статус:** обязателен для всей разработки  
**Принцип:** подробно по смыслу, лаконично по форме  
**Хранитель стандарта:** Product Manager  
**Исполнители:** все роли (TL, ARCH, Dev, SIM, PLAT, QA)

---

## 1. Правило

> **Код без актуальной документации не считается сданным.**  
> Документация — часть продукта, не «потом допишем».

Вся разработка в `signaldeck/` ведётся с **подробной лаконичной** документацией:

- **Подробная** — достаточно, чтобы PO, PM, другой агент или новый человек воспроизвели смысл, запуск и контракты без устных пояснений.
- **Лаконичная** — без воды, повторов и простыней; короткие абзацы, таблицы, списки, примеры.

Запрещены: романы без структуры, копипаст кода вместо описания, устаревшие docs «на будущее», пустые README-заглушки у новых модулей.

---

## 2. Слои документации

| Слой | Где | Что описывает | Кто отвечает |
|------|-----|---------------|--------------|
| Продукт / governance | `docs/` | Vision, роли, MVP, стек, контракты | PM (+ ARCH по техчасти) |
| Архитектура | `docs/architecture/` | C4, ADR, последовательности | ARCH |
| Сервис / модуль | `<module>/README.md` | Назначение, запуск, env, API/топики | Владелец зоны (Dev/PLAT/SIM) |
| Контракты | `docs/` + OpenAPI / schema | Протоколы между частями | ARCH + владелец |
| Эксплуатация | `deploy/README.md`, корневой README | Compose, порты, demo path | PLAT |
| QA | `docs/qa/` | Чеклисты, отчёты приёмки | QA |
| Changelog фазы | `docs/changelog/` | Статусы приёмки PM | TL / PM |
| **Рабочие логи** | `logs/` | Сделано / план / подводные камни по сессиям | PM + команда |

Целевая структура (наращивается по фазам, не всё сразу пустыми файлами):

```text
signaldeck/
  README.md                 # вход: что это, ссылки, как поднять
  docs/
    documentation-standard.md
    governance.md
    product-manager.md
    product-brief.md
    mvp-plan.md
    stack-decision.md
    device-contract-*.md
    team.md
    architecture/           # ADR, C4
    qa/                     # отчёты и чеклисты
    changelog/              # по желанию TL/PM
  agents/                   # мандаты ролей
  control|ingest|web|.../
    README.md               # обязателен при появлении модуля
```

## 3. Стиль: «подробно и лаконично»

### Делать

- Заголовок → 1–2 предложения сути → таблица/список → пример при необходимости.
- Писать **для читателя, который не был в чате**.
- Фиксировать решения и **негативные решения** (что сознательно не делаем).
- Датировать/версионировать контракты и ADR.
- Обновлять docs **в том же пакету сдачи**, что и код.

### Не делать

- Дублировать один и тот же текст в трёх файлах — дать ссылку на источник правды.
- Описывать каждую строку кода.
- Оставлять `TODO: document later` на сдаваемом scope.
- Писать документацию «на английском и русском сразу» без нужды (язык продукта docs: **русский**, идентификаторы кода — как в коде).

### Шаблон модуля (`<module>/README.md`)

```markdown
# <Имя модуля>

## Назначение
Одно короткое «зачем».

## Границы
Что входит / что не входит (ссылка на plane или ADR).

## Запуск
Команды, порты, зависимости от Compose.

## Конфигурация
Таблица env / файлов.

## Контракты
Ссылки на OpenAPI, MQTT topics, WS events + 1 пример.

## Разработка
Как гонять локально, линтер/тесты.

## Известные ограничения
Только актуальное для текущей фазы.
```

### Шаблон ADR (`docs/architecture/adr-NNN-*.md`)

- Контекст → Решение → Последствия → Статус (proposed/accepted/superseded).
- Объём: обычно ≤ 1–1.5 экрана.

## 4. Definition of Done (документация)

Работа **не сдаётся** Tech Lead / PM, если не выполнено релевантное:

| Изменение | Минимум docs |
|-----------|----------------|
| Новый сервис/модуль | `README.md` по шаблону |
| Новый/изменённый API | OpenAPI + кратко в README модуля |
| MQTT/WS/device protocol | обновлён `device-contract` и/или ADR |
| Решение, меняющее границы системы | ADR |
| Compose / порты / env | `deploy/README` + корневой README при необходимости |
| Фаза закрывается | краткий phase note: что сделано, как демо, ограничения |
| Багфикс, меняющий поведение | одна строка в changelog/phase note или README |
| Сессия разработки / инцидент | запись в `logs/` (сделано, план, подводные камни) |

Tech Lead **обязан** вернуть пакет без docs.  
PM **обязан** отклонить приёмку исполнения, если документация устарела или отсутствует по сдаваемому scope.

## 5. Источник правды

| Тема | Канон |
|------|--------|
| Смысл продукта, роли | `docs/governance.md`, `docs/product-brief.md` |
| Роль PM | `docs/product-manager.md` |
| План MVP | `docs/mvp-plan.md` |
| Стек | `docs/stack-decision.md` |
| Устройства | `docs/device-contract-*.md` |
| Команда | `docs/team.md`, `agents/*` |
| Как писать docs | **этот файл** |
| Поведение кода | код + README модуля + OpenAPI; не противоречить docs |

При расхождении кода и docs — **баг сдачи**: либо чинится код, либо обновляются docs в том же пакете. Молчаливое «в коде уже не так» запрещено.

---

## 6. Обязанности по ролям

| Роль | Документационный долг |
|------|------------------------|
| **PM** | Продуктовые docs; контроль наличия docs в приёмке; индекс в корневом README |
| **Tech Lead** | Phase notes; отказ в техприёмке без docs; нет рассинхрона между модулями |
| **Architect** | ADR, C4, актуальность контрактов |
| **BE-CTRL / BE-DATA / FE / SIM / PLAT** | README своей зоны; примеры; обновление контрактных кусков |
| **QA** | Чеклисты и отчёты в `docs/qa/`; ссылки на шаги воспроизведения |
