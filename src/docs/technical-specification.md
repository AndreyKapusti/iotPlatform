**Статус:** утверждено решениями PO (2026-10-06)  
**Версия документа:** 1.0  
**Связанные docs:** [product-brief.md](product-brief.md), [mvp-plan.md](mvp-plan.md), [device-contract-v0.md](device-contract-v0.md), [stack-decision.md](stack-decision.md)

## 1. Цель и контекст

### 1.1. Зачем

Собрать контур «устройство → телеметрия → дашборд → (опционально) управление» без написания бэкенда, хранения и UI с нуля под каждый пилот и без тяжёлого enterprise-UX существующих платформ.

### 1.2. Для кого

| Сегмент | Использование |
|---------|----------------|
| Производство | Пилоты мониторинга линий/цехов |
| Вузы / лаборатории | Стенды, дипломы, учебные контуры |
| DIY / обучение | Вторичный сегмент на ранней стадии |

### 1.3. Проблема и решение

**Проблема:** нет простого самохостируемого пути от credentials устройства до живого конструктора дашборда с real-time обновлением.

**Решение — SignalDeck:** устройство (или симулятор) объявляет capabilities; платформа сохраняет схему и предлагает виджеты; пользователь собирает дашборд drag-and-drop; телеметрия идёт по data plane с обновлением UI в реальном времени.

### 1.4. Назначение этого ТЗ

Формальная фиксация объёма текущей поставки: **MVP + уже принятые расширения**. Не является runbook’ом облачного прода и не заменяет Device Contract.

## 2. Объём и границы

### 2.1. Входит (текущая поставка)

**Ядро MVP**

- Регистрация и вход пользователя.
- Создание устройства, выдача credentials (API key / MQTT).
- Приём announce (capabilities) и telemetry (readings) от устройства/симулятора.
- Просмотр схемы устройства; палитра виджетов строится по capabilities.
- Один или несколько дашбордов **на одно устройство**; сохранение layout.
- DnD-редактор с ≥ 3 типами визуализаций (минимум: line, gauge/KPI, boolean indicator).
- Real-time обновление виджетов без ручного refresh; подгрузка history при открытии.
- Статус online / last seen по активности устройства.
- Развёртывание через Docker Compose на чистой машине; демо-симулятор одного устройства.

**Уже принятые расширения (входят в текущую поставку)**

- Профиль пользователя: ФИО, дата рождения, email, телефон, организация, должность, часовой пояс; логин read-only.
- Несколько дашбордов на устройство; режимы просмотр / редактирование.
- Тема оформления (light / dark / system); локализация UI ru/en.
- Ресайз виджетов мышью в edit; именованные акценты виджета (читаемые в обеих темах).
- Обзор флота (Overview) и лента событий (Events) на стороне UI.
- Toggle актуатора в UI: допускается **stub/демо** без обязательного E2E MQTT command.

### 2.2. Не входит (сознательно)

- Реальная прошивка Arduino/ESP и автообнаружение железа.
- Обязательная доставка команд актуатору по MQTT/HTTP (post-MVP / polish).
- Несколько устройств на одном дашборде.
- Автоматизация сценариев, push/email/SMS-алерты, эскалации (кроме локальных offline-подсказок в UI).
- OAuth, multi-org, сложные RBAC, биллинг, marketplace шаблонов.
- Облачный SaaS, Kubernetes, Kafka «с первого дня».
- Подтверждение email, 2FA, загрузка аватара (см. [roadmap-future.md](roadmap-future.md)).

### 2.3. Платформа развёртывания

**В scope:** Docker Compose, самохостинг.  
**Вне scope этого ТЗ:** обязательный прод-VPS с доменом/HTTPS как критерий приёмки (может описываться отдельно).

## 3. Функциональные требования

Нумерация: FR-*. Проверяемые сценарии без привязки к языку реализации.

### 3.1. Учётная запись и профиль

| ID | Требование |
|----|------------|
| FR-01 | Пользователь регистрируется (email, username, password) и входит в систему. |
| FR-02 | Неверный пароль отклоняется; защищённые операции недоступны без сессии. |
| FR-03 | Пользователь просматривает и редактирует профиль: фамилия, имя, отчество, дата рождения, email, телефон, организация, должность, timezone. |
| FR-04 | Username в профиле не меняется через UI профиля. |
| FR-05 | Смена email на уже занятый другим пользователем отклоняется. |
| FR-06 | Дата рождения в будущем отклоняется. |

### 3.2. Устройства и схема

| ID | Требование |
|----|------------|
| FR-10 | Пользователь создаёт устройство и получает credentials для подключения. |
| FR-11 | Пользователь видит список устройств и карточку устройства (имя, ключ/подсказки подключения, last seen). |
| FR-12 | После announce устройство показывает capabilities (имя, тип, role, unit, min/max при наличии). |
| FR-13 | Неверный API key на ingest отвергается. |
| FR-14 | UI отображает online/offline на основе last seen (порог задаётся продуктом; ориентир — порядка минуты). |

### 3.3. Телеметрия и real-time

| ID | Требование |
|----|------------|
| FR-20 | Платформа принимает readings, ключи которых соответствуют capabilities. |
| FR-21 | При открытии дашборда подгружается history по метрикам layout. |
| FR-22 | Новые точки доставляются в UI в реальном времени без ручного обновления страницы. |
| FR-23 | Поддерживаются типы значений: number, boolean, string (в рамках контракта устройства). |

### 3.4. Дашборды

| ID | Требование |
|----|------------|
| FR-30 | Пользователь создаёт, открывает, переименовывает (если UI даёт), удаляет дашборд устройства. |
| FR-31 | На одном устройстве допускается несколько дашбордов. |
| FR-32 | В режиме редактирования: добавление виджета из палитры (только метрики из capabilities), перемещение, изменение размера, удаление, сохранение layout. |
| FR-33 | В режиме просмотра панели редактирования скрыты; виджеты показывают live/history. |
| FR-34 | Доступны ≥ 3 типа виджетов: график (line), числовой индикатор/gauge, boolean indicator. |
| FR-35 | Для actuator boolean доступен toggle; доставка команды на устройство **не обязательна** для приёмки (stub/демо допустим). |
| FR-36 | Пользователь задаёт акцентный цвет виджета из фиксированной палитры; цвет остаётся читаемым в светлой и тёмной теме. |
| FR-37 | Layout сохраняется и восстанавливается после перезагрузки. |

### 3.5. Настройки и оболочка UI

| ID | Требование |
|----|------------|
| FR-40 | Пользователь переключает тему: light / dark / system. |
| FR-41 | Пользователь переключает язык интерфейса: ru / en. |
| FR-42 | Есть экран обзора (Overview) с сводкой по устройствам пользователя. |
| FR-43 | Есть экран ленты событий (Events) на основе клиентской/локальной агрегации событий флота. |

### 3.6. Демо и симулятор

| ID | Требование |
|----|------------|
| FR-50 | В составе поставки есть симулятор, который регистрирует/использует demo-устройство, делает announce и периодически шлёт telemetry. |
| FR-51 | Happy path выполняется без ручных вызовов API «для галочки». |

## 4. Нефункциональные требования

Только требования, существенные для продукта. SLA / uptime **не заданы** заказчиком.

| ID | Область | Требование |
|----|---------|------------|
| NFR-01 | Развёртывание | Система поднимается через Docker Compose на чистой машине с Docker Compose v2. |
| NFR-02 | Real-time | Ориентир: publish → точка в UI &lt; ~200 ms на локальном стенде (пилот). |
| NFR-03 | Нагрузка (ориентир) | Пилот: порядка 100–1k устройств online, 100–1k msg/s; стресс-цифры для отчёта — отдельно, не критерий блокировки UX-MVP. |
| NFR-04 | Хранение | Ориентир retention сырых метрик 30–90 дней (+ rollup позже); жёсткая политика purge в MVP не обязательна. |
| NFR-05 | Безопасность (минимум) | Пароли хранятся хэшированными; API пользователя защищены сессией/JWT; credentials устройства не отдаются третьим лицам без auth пользователя. |
| NFR-06 | Совместимость клиента | Современный desktop-браузер (Chrome/Firefox/Edge актуальные); UI desktop-first. |
| NFR-07 | Масштабируемость | Разделение control plane и data plane; горизонтальный scale ingest — цель архитектуры, не требование одного процесса. |
| NFR-08 | Документация | Актуальные product/docs сдаются вместе с поставкой ([documentation-standard.md](documentation-standard.md)). |

**Известный технический долг (не блокирует FR-22, но фиксируется):** history/WS на data plane могут не требовать JWT в текущей реализации — усиление auth планируется отдельно.

## 5. Роли и права

### 5.1. Роли пользователей системы

| Роль | Права |
|------|--------|
| Неаутентифицированный | Регистрация, вход. |
| Аутентифицированный пользователь | Свои устройства, capabilities (чтение), дашборды CRUD, профиль, настройки UI, telemetry своего устройства через UI. |

Сложные org-роли, admin-панель, делегирование между пользователями — **вне scope**.

### 5.2. Роли capability устройства (не RBAC)

| Role | Смысл |
|------|--------|
| `sensor` | Метрика только на чтение в UI. |
| `actuator` | Допускается виджет управления; реальная команда на устройство — опционально. |

### 5.3. Идентичность устройства

Устройство аутентифицируется API key (и/или MQTT credentials), выданными платформой владельцу устройства.

## 6. Данные и интеграции

### 6.1. Сущности

| Сущность | Содержание |
|----------|------------|
| User | Учётные данные + поля профиля |
| Device | Имя, владелец, API key, активность, last seen |
| Capability | name, type, role, unit, min/max, schema_version |
| Reading / metric point | device, metric, value, timestamp |
| Dashboard | device, name, layout (виджеты: type, metric, geometry, title, accent) |

### 6.2. Источники данных

| Источник | Данные |
|----------|--------|
| Пользователь (UI) | Регистрация, профиль, layout дашбордов, настройки UI |
| Устройство / симулятор | Announce capabilities, telemetry readings |
| Платформа | Online/last seen, history, real-time push в UI |

### 6.3. Внешние интеграции (транспорт)

| Канал | Назначение |
|-------|------------|
| MQTT | announce, telemetry; command — опционально |
| HTTP ingest | Fallback приёма данных устройства |
| WebSocket (или эквивалент push) | Real-time в UI |
| HTTP control API | Auth, devices, capabilities read, dashboards, profile |

Контракт JSON: [device-contract-v0.md](device-contract-v0.md).

### 6.4. Внешние SaaS

Обязательных внешних облачных сервисов нет (самохостинг). Почта для verify, object storage для аватаров — вне scope.

## 7. Ограничения и допущения

### 7.1. Стек (задан)

| Слой | Технология |
|------|------------|
| Control plane | Python, FastAPI |
| Data plane | Go (ingest, history, realtime) |
| Broker | Mosquitto (MVP) |
| БД | PostgreSQL + TimescaleDB |
| UI | React + TypeScript |
| Упаковка | Docker Compose |
| Устройство на MVP | Симулятор по Device Contract |

Детали: [stack-decision.md](stack-decision.md), [adr-001-hybrid-planes.md](architecture/adr-001-hybrid-planes.md).

### 7.2. Допущения

- На этапе приёмки достаточно симулятора вместо железа.
- Один дашборд привязан к одному устройству (не multi-device canvas).
- Имена метрик — opaque-строки из capabilities; UI не хардкодит конкретные датчики.
- Бюджет, календарный дедлайн договора, юридические требования и SLA **не заданы** заказчиком в рамках этого ТЗ.
- Ориентир календаря разработки MVP: порядка 2.5–3 месяцев (из плана фаз) — не жёсткий контрактный срок.

### 7.3. Риски

| Риск | Митигация |
|------|-----------|
| Публичный history/WS без auth | Закрыть auth post-MVP; не светить порты ingest в интернет без proxy/ACL |
| Дефолтные секреты в demo compose | Перед внешней сетью сменить JWT/БД/пароли |
| Рост объёма Timescale | Retention/rollup; запас диска на VPS |
| Stub toggle vs ожидание железа | Явно помечать «демо» в UI до E2E command |

## 8. Критерии приёмки

Поставка считается выполненной, если выполнены все пункты ниже.

### 8.1. Инфра и демо

- [ ] `docker compose up --build` (из `deploy/`) поднимает сервисы на чистой машине с Docker.
- [ ] Профиль demo поднимает симулятор; есть рабочий demo-login / demo-устройство **или** пользователь создаёт устройство и подключает симулятор своими credentials.
- [ ] Health endpoints control/ingest отвечают.

### 8.2. Happy path (обязательный)

- [ ] Регистрация + вход.
- [ ] Устройство видно; capabilities появляются после announce.
- [ ] Создан/открыт дашборд; добавлены виджеты line, gauge (или KPI), indicator; layout сохранён.
- [ ] Live-обновление без refresh; history при открытии.
- [ ] Online/offline отражает остановку/работу источника телеметрии.

### 8.3. Расширения текущей поставки

- [ ] Профиль: сохранение и перечитывание полей после reload.
- [ ] ≥ 2 дашборда на одно устройство (создание второго).
- [ ] View vs edit: в просмотре нет палитры/ресайза.
- [ ] Тема и язык переключаются и сохраняются в клиенте.
- [ ] Ресайз виджета мышью в edit; выбор accent.
- [ ] Доступны экраны Overview и Events.
- [ ] Toggle актуатора работает в UI (допустим stub без реальной команды на брокер).

### 8.4. Негатив

- [ ] Неверный пароль → отказ во входе.
- [ ] Неверный API key на ingest → отказ.
- [ ] Битый/невалидный payload устройства → отказ с ошибкой клиента (4xx), без падения сервиса.

### 8.5. Документы

- [ ] Настоящее ТЗ, product brief, device contract, stack decision актуальны относительно поставки.
- [ ] Есть QA-чеклист MVP ([qa/mvp-checklist.md](qa/mvp-checklist.md)) для прогона.

### 8.6. Явно не требуется для приёмки по этому ТЗ

- E2E MQTT command на актуатор.
- Прод-домен, HTTPS, managed cloud.
- Прошивка ESP/Arduino.
- Нагрузочный отчёт на 10k устройств (желательно для диплома, не блокер UX-приёмки).
